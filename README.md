# Campus Radar · 校园机会雷达

面向在校学生（尤其大一新生）的校园活动与机会信息平台。把来源不同、格式不一、质量参差的校园信息，整理成「**现在该做什么**」的清晰判断；同时给同学一个发布与反馈的通道，给管理者一套审核与追溯的机制。

**纯静态站点，零后端依赖** —— 打开链接即可使用，账号登录、投稿审核、举报处理全部可用。

---

## 一、这个产品解决什么问题

校园信息的问题不在「信息太少」，而在**信息之间无法比较**。同一场活动可能有三条通知、两种格式、四个时间点；一条招募可能只写了「加微信详聊」；一个链接可能今天有效明天失效。

新生尤其吃亏——他们还没有建立起「哪个渠道的信息可信」「这条通知是不是被改过」的判断经验。

Campus Radar 把这类隐性判断显性化：

| 材料里的真实问题 | 产品给出的处理 |
|---|---|
| 01 训练营被 09 号补充通知改了时间和地点 | 自动合并为一条，高亮变更点，旧版本折叠在下方供核对 |
| 03 招募被 20 号补充说明改了名额 | 主卡直接显示「开发方向名额已满」 |
| 24「零门槛、日结，加私人微信」 | 标记为高风险，逐条列出可疑特征并给出安全提示 |
| 25 标题写技术交流，正文是商家购买链接 | 标记为「标题与正文不一致 + 商业推广」 |
| 06 / 12 / 16 / 22 / 23 关键字段缺失 | 不编造、不猜测，明确列出「材料中未提供的信息」并建议核实 |
| 19 报名已截止但活动还没办 | 状态精确显示为「报名已截止 · 可候补」，而不是笼统的「即将开始」 |

## 二、核心功能

### 1. 状态机驱动的信息浏览

不把一切都叫「进行中」。每条信息会落到 10 种互斥状态之一：

`进行中` · `即将开始` · `报名即将截止` · `报名开放` · `报名已截止·可候补` · `待开始` · `长期开放` · `已结束·回放待出` · `状态待确认` · `已结束`

### 2. 多维度筛选与两种视图

- **快捷场景**：我现在能参加 / 48 小时内节点 / 适合新生 / 仅校方与学院 / 我收藏的 / 今天
- **常规维度**：信息来源、信息类别、当前状态
- **展示方式**：卡片列表（快速扫读）与时间线（按天排布，便于发现撞车）

### 3. 我的清单与时间冲突检测

收藏后自动检测时间重叠。材料里 **9月21日 19:00—20:30** 挤了三场活动（01 训练营首训、11 科研入门、14 Git 工作坊），加入清单后会直接给出冲突警告。

### 4. 学生自主发布（需审核）

学生可发布约球、组队、兴趣活动等信息，提交后进入待审核队列，通过后才对其他同学可见。

### 5. 管理端审核台

管理端可发布校方 / 学院级信息（直接上架），并处理三类事务：

- **审核队列**：通过 / 要求补充 / 驳回（后两者必须填写理由，理由会展示给发布者）
- **举报队列**：同学举报 → 管理员判定成立或忽略 → 内容被处理时举报自动结案
- **管理概览**：待审积压、投稿通过率、来源与风险分布、完整操作日志

### 6. 权限分级

| 能力 | 游客 | 学生端 | 管理端 |
|---|:--:|:--:|:--:|
| 浏览已上架信息 | ✅ | ✅ | ✅ |
| 收藏 / 我的清单 | — | ✅ | ✅ |
| 发布信息 | — | ✅ 需审核 | ✅ 直接上架 |
| 举报可疑信息 | — | ✅ | — |
| 审核 / 驳回 / 下架 | — | — | ✅ |
| 数据看板与审计日志 | — | — | ✅ |

权限的判定在数据层执行，界面按钮的显示只是体验，**不是**权限边界。

## 三、自主设计的实用功能

### 1. 信息修订链自动合并 ★

**这是材料里最隐蔽、也最容易坑到人的一点。** 26 条信息中有 2 条不是新活动，而是对已有活动的修订：

- `09` 修改了 `01` 的首次训练时间与地点
- `20` 修改了 `03` 的名额情况

产品识别出这层关系后，主卡直接展示最终生效的版本，把变更点逐条列出，并把补充通知原文折叠在下方供核对。新生不会按旧信息跑到错误的教室。

### 2. 内容风险雷达

一套规则，**同时用于三个环节**：

```
投稿实时预检  →  入库复核  →  管理端审核参考
```

规则覆盖：引导至私人联系方式、商品推广与购买引导、先付费或索取证件、夸大招聘话术、校外链接。

含高风险特征的内容会**被数据层直接拒绝入库**，从机制上防止绕过前端预检。

### 3. 投稿质检与重复检测

提交前实时给出 100 分制的信息完整度评分，逐条说明缺什么、有什么问题。

重复检测用**字符二元组 Jaccard 相似度**比较标题，超过 45% 提示疑似重复——避免同一位同学反复提交同一个活动，把审核队列塞满。

### 4. 新生模式

一键隐藏明确不适合大一的信息（如 13 号「仅限大二及以上」），并对含糊的表述做正向判断：「零基础可参加」「面向全校」「不限基础」都会被视为新生友好。

## 四、我主动发现并处理的一个关键问题

**问题：只有人工审核的开放投稿，必然走向两个极端——要么审核员被淹没，要么审核变成走过场的橡皮图章。**

材料里 26 条信息已经暴露了信息质量的分布：既有规范的官方通知，也有「加微信详聊」和「标题写交流、正文卖货」的内容。如果放开让学生投稿，审核量会迅速超过人工处理能力；如果为了省事一律放行，平台就会退化成广告墙。

**处理方式：把审核负担前移到发布端，并把机器预判交给审核员。**

具体做了三件事：

1. **发布端实时预检** —— 提交前就指出风险与缺失，让发布者自己先改一遍，而不是提交后被驳回再改。
2. **数据层独立复核** —— 前端预检可以被绕过，所以数据层会重新跑一遍扫描；命中高危特征直接拒绝入库。
3. **审核员看到的是带证据的判断** —— 每条待审投稿都携带完整度得分、命中的风险规则、疑似重复项。审核员不需要从零读文本，而是在机器预判的基础上做人的判断。

这个设计的核心不是「用机器替代人」，而是**让人把注意力花在机器判断不了的地方**。

配套还有**举报闭环**：平台允许同学发内容，就必须给同学一个反馈问题的通道。举报进入管理端队列，内容被下架时关联举报自动结案，全过程写入审计日志。

## 五、技术架构

**前端**：原生 ES Modules + 手写 CSS。零框架、零构建、零依赖。

**数据层**：可插拔的两种实现，接口签名完全一致，视图层无需感知：

| 模式 | 实现 | 存储 | 适用场景 |
|---|---|---|---|
| `local`（默认） | `src/api/local.js` | 浏览器 localStorage | GitHub Pages、任意静态托管、双击打开 |
| `remote` | `src/api/client.js` | EdgeOne Makers 云函数 + Blob | 需要多设备同步时 |

切换方式：修改 `index.html` 中的 `window.__CAMPUS_RADAR_MODE__`。

**密码处理**：即便是纯静态模式，密码也使用 PBKDF2-SHA256（10 万次迭代、每用户独立 salt）派生后存储，不落明文，比较使用恒定时间算法。

> 需要说明的是：纯前端环境无法阻止使用者读取自己的 localStorage。这里的目标是「不制造额外的明文泄露面」，而不是提供真正的服务端安全。真实多用户场景应使用 `remote` 模式。

**数据单一来源**：内置的 26 条信息只维护一份（`src/data/activities.js`）。远端正则所需的副本由 `tools/gen-seed.mjs` 生成，避免两处手工维护导致不一致。

## 六、运行方式

### 最简单：直接打开

```
双击 index.html
```

或在项目目录启动任意静态服务器：

```bash
python -m http.server 5173
# 然后访问 http://localhost:5173
```

### 在线访问

部署在 GitHub Pages 上，见仓库的 Pages 链接。

### 演示账号

| 角色 | 用户名 | 密码 | 用途 |
|---|---|---|---|
| 管理端 | `admin` | `admin123` | 审核投稿、发布官方信息、查看看板 |
| 学生端 | `student` | `student123` | 收藏、投稿、举报 |

登录弹层里点击演示账号可以一键填入。也可以自己注册新账号（管理员需要邀请码 `RADAR-ADMIN`）。

### 推荐体验路径

1. 以**游客**浏览发现页，观察状态徽章与倒计时
2. 打开 01 号信息的详情，看「信息更新记录」如何合并 09 号通知
3. 打开 24 号信息的详情，看风险特征如何被逐条列出
4. 登录 `student`，收藏 01、11、14，到「我的清单」看时间冲突提醒
5. 在「发布」页写一条含「加微信」的内容，观察质检拦截
6. 切到 `admin`，到「审核台」处理刚才的投稿
7. 回到「管理概览」，看审计日志记录的每一步操作

## 八、如果继续开发

按优先级排列：

1. **信息源接入与去重** —— 目前信息靠人工录入。真实场景应支持从学院通知页、公众号等渠道自动抓取，并与已有信息做相似度匹配，自动提示「这条可能是某条通知的更新」。这正是修订链功能的自然延伸。
2. **变更通知** —— 当已收藏的信息被修订或下架时，主动提醒加入清单的同学。
3. **服务端同步** —— 把 `local` 模式的数据层替换为 `remote`，让多台设备共享同一份数据与审核队列。数据层已经按可替换的方式设计好，主要工作是补齐部署与鉴权细节。
4. **审核规则的持续运营** —— 当前风险规则是固定正则。更有价值的做法是让管理员能标记误判，逐步把规则调整成贴合本校语境的版本。
5. **导出为日历** —— 把清单导出为 ICS，接进手机日历，让「报名截止」真正进入同学的日程系统。

## 九、关于数据与取材的说明

- 全部校园信息来自考核题目提供的 26 条模拟材料，**未补充任何题目之外的事实**。
- 题面未给出的字段（如 12 号费用、06 号报名截止、16 号截止时间）一律标注为「材料中未提供」，不做推测。
- 材料中只给出日期而未给具体时刻的（如 13 号「9月21日截止」），按当日 23:59 处理并在界面注明「具体时刻未注明」，避免传递虚假的精确度。
- 默认的 `local` 模式下，数据保存在你自己的浏览器中，清除浏览器数据会回到初始状态；页面内提供了重置入口。
- 演示账号与默认管理员邀请码仅用于体验。若要用于真实场景，请切换到 `remote` 模式并更换全部密钥。
